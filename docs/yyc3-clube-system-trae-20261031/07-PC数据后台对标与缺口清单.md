# 📊 PC 数据后台对标与缺口清单

> **对标对象**：在用「智慧商家桌面版」PC 数据后台（`pc.g-hi.com`，只读登录采集）
> **辅助基线**：`docs/YYC3-艺人管理-开发文档/智慧商家桌面版使用说明《修订版》.docx`（7 章 42 小节）
> **被对标对象**：CMS 当前仓（`app/dashboard` 路由 + `components/layout/sidebar.tsx`）
> **账号说明**：登录账号仅用于本次只读采集，文档中不记录任何凭据；未导出、未修改任何业务数据。
> **账号解封**：已提交技术反馈，预计 **48 小时**；解封后补采 27 张报表列头。
> **补充基线**：PC 端另有非菜单入口「艺人设置」7 项/13 子项（资料必填 2、报备 4、签退间隔、手动下钟、未签到上钟、台票购买 3、上钟模式），逐项语义见 [`10-艺人设置配置规范.md`](./10-艺人设置配置规范.md)；艺人档案/报备/上下钟/台费/台票的**管理编辑在 App**，CMS 只做读取/报表/配置。
> **全量路由清单**：160/160 页面的路由、标题、筛选、列头与按钮结构见 [`08-PC数据后台全量页面清单.md`](./08-PC数据后台全量页面清单.md)；其中 27 张报表列头待补（采集后账号被风控封禁，详见 08 §0）。

## 0. 直接回答：用“在用系统”做基线，能否完整指导缺失？

**能，但要分三层说清楚：**

| 层次 | 在用系统能提供什么 | 不能提供什么 | 结论 |
| --- | --- | --- | --- |
| **页面/菜单层** | 7 大模块、**160 个菜单项**（含报表 10 组 98 张）的完整结构 | 页面内部全部字段、弹窗、校验规则 | ✅ **可完整指导“缺哪些页”** |
| **字段/筛选层** | 列表页筛选条件、列头、导出/导入入口、门店切换、营业日口径 | 字段精度、状态机、权限矩阵、接口协议 | 🟡 **可指导 70%，其余需业务/财务确认** |
| **规则/数据层** | 手册中的计费、低消、抹零、寄存、审批等规则描述 | 数据库结构、API 契约、历史数据、异常分支 | 🔴 **必须另行补文档** |

**一句话**：在用系统解决的是「**做什么页面、看什么数据**」；手册解决的是「**按什么规则算**」；CMS 代码决定「**已经做到哪一步**」。三者对齐后，缺口可以从“感觉缺”变成“**可编号、可验收、可排期**”。

## 6. 接口/路由对齐建议

### 6.1 实测在用人路由（只读采集样本）

| 功能 | 在用系统路由 |
| --- | --- |
| 员工列表 | `#/staff_manage/employee_list` |
| 艺人列表 | `#/staff_manage/waiter_list` |
| 门店列表 | `#/system_set/store_list` |
| 支付流水 | `#/sale_manage/pay_flow` |
| 预订列表 | `#/sale_manage/book_list` |
| 艺人上下钟明细报表 | `#/finance_report/waiter_report/wr_ydm_report` |

> 命名提示：在用系统内部用 `waiter` 指代“艺人”（`waiter_list`、`waiter_report`），与 CMS 的 `artist` 命名不同。**建议 CMS 统一用 `artist`，但在导入/对接层保留 `waiter` 别名映射，避免语义丢失。**

/dashboard/artists/fee-accounts    ← 台费账户
/dashboard/artists/attendance      ← 报备

/dashboard/reports/members/[slug]    ← 会员 12 张
/dashboard/reports/liquor/[slug]     ← 酒水 10 张
/dashboard/reports/artist/[slug]     ← 艺人 10 张（保留现有 4 个路径）
/dashboard/reports/product-sales/[slug]
/dashboard/reports/product-profit/[slug]
/dashboard/reports/others/[slug]
/dashboard/reports/flower/[slug]
/dashboard/reports/customers

### 6.3 契约要求（每个列表/报表）

- 查询：`storeId`、`businessDateFrom/To`、`roomArea`、`roomType`、`payType`、`payStatus`、`orderSource`、`staffId`、`operatorId`、`memberCardNo`、`booker`、`page/pageSize`
- 响应：`total`、`rows`、`summary`（金额/数量小计）、`source`（db/mock）
- 导出：同筛选条件 + `operator` + `requestId`，写 `export_audit`
- 权限：接口级校验（非仅前端隐藏）
- 口径：`businessDate` 统一由服务端计算（08:00 切日）

## 9. 风险与边界

| 风险 | 说明 | 缓解 |
| --- | --- | --- |
| 第三方知识产权 | 在用系统与手册属厦门巨嗨科技；界面结构可参考，素材/文案不可复制 | 只做结构与字段对标；自建设计语言；手册内部参考、不对外分发 |
| 只读采集的局限 | 无 API/DB 文档，字段精度、状态机、异常分支未知 | 以“页面可达 + 字段可查”为第一阶段目标；规则逐条找业务确认 |
| 口径不一致 | 营业日、退款、赠送、挂账、交接班口径可能有门店差异 | 建《报表口径字典》，财务签字后冻结 |
| 端侧越界 | 把 POS 收银交互搬进 CMS，导致后台变重 | 明确 CMS 不承载 POS；只消费 OPS 交易数据 |
| 数据隐私 | 实时系统含真实门店/员工/订单数据 | 不导出业务数据、不截图入库、不写凭据；仅记录菜单结构 |
| 大文件入库 | 5.2 MB 手册未跟踪 | Git LFS 或外链 + SHA-256；补来源/授权 README |
