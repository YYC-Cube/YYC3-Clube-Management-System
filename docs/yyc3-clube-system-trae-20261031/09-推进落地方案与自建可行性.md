# 🚀 PC 数据后台推进落地方案与自建可行性

> **输入基线（两次采集）**
> 1. **规则基线**：`智慧商家桌面版使用说明《修订版》.docx` —— 7 章 42 小节（计费、低消、抹零、寄存、审批等）。
> 2. **结构基线**：在用 PC 数据后台实测 —— **160 / 160 页面**（7 大模块、98 张报表、26 项设置），见 [`08-PC数据后台全量页面清单.md`](./08-PC数据后台全量页面清单.md)。
> 3. **缺口基线**：[`07-PC数据后台对标与缺口清单.md`](./07-PC数据后台对标与缺口清单.md) 的 14 项缺口。
> 4. **现有实现**：CMS（Next 16 + 65 页 + 93 API + 艺人报表真实库）、OPS（多租户/RLS/POS/计价内核）。

## 0. 结论先行

### 0.1 能不能“缺失自建”？

**能自建 PC 数据后台的主体，但不能 100% 自建。** 按页面当量拆分：

| 分类 | 页面当量 | 占比 | 判定 |
| --- | --- | --- | --- |
| **已有可读结构，可立即自建** | 约 **95 / 124** | 77% | 🟩 可自建 |
| **需补采列头/口径确认后自建** | 约 **29 / 124** | 23% | 🟧 待补采/待确认 |
| **必须外部依赖，不能完整自建** | 硬件控制、支付清算、短信/版权、第三方素材、历史数据迁移 | — | 🟥 不可自建（仅能做配置/适配层） |

> 另有 **1 个非菜单入口页**：艺人设置（7 项配置），单列补充，不计入 124；PC 截图已确认，见 08 §2.8。

### 0.2 三个硬约束（先解决再排期）

| # | 约束 | 影响 | 处理 |
| --- | --- | --- | --- |
| 1 | **账号被风控封禁**（“账号异常已被封禁”） | 27 张报表列头 + 2 个缺失多 Tab 页（花管理、平板点歌）无法补采 | **已提交技术反馈，预计 48 小时解封**；解封前用已知 71 张并行开工 |
| 2 | **27 张报表列头未取到** | 报表只能搭框架，不能冻结字段 | 解封后单会话补采；补采前先做框架 + 已知列头 |
| 3 | **报表口径未确认**（退款/赠送/挂账/交接班/版权费/业绩系数） | 报表数字不可验收 | 财务签字冻结《报表口径字典》 |

### 0.3 推荐节奏

```
Phase 0 基线冻结（1 周）
   └─ 解封补采（48h 后） + 报表口径 v0 + 数据模型 ADR + OpenAPI v0
Phase 1 核心闭环（3~4 周）—— 解封前即可并行开工
   └─ 门店上下文 + 支付/预订 + 艺人只读域/艺人设置 + 商品规则 + 仓库主数据 + 报表 MVP(手册4组/8张)
Phase 2 全量对齐（6 周）
   └─ 报表 98 张扩展（Wave 2/3）+ 设置 19 项 + 权限/导入导出/审计
Phase 3 外部依赖与差异化（季度）
   └─ 硬件配置/适配、支付通道、短信/卡券、AI/IoT
```

> **并行原则**：报表全做、艺人只读域、商品规则、仓库主数据、报表框架**互不依赖**；不等 27 张列头补齐，先把契约、模型、页面骨架与已知 71 张报表跑起来。

## 3. 不能自建 / 不建议自建的清单（红线）

| # | 不可自建项 | 原因 | 可做的替代 |
| --- | --- | --- | --- |
| 1 | VOD、点歌屏、电视屏、门牌机、打印机**指令级控制** | 无厂商 SDK/协议文档；逆向风险高 | 配置管理 + 状态展示 + 预留 `device_adapter` 接口；拿到 SDK 后接 |
| 2 | 微信/支付宝/抖音/团购**支付与清算** | 需商户号、签约、证书、回调验签、对账 | 先做支付流水查询/对账导入；通道对接作为独立 Phase 3 任务 |
| 3 | 短信、卡券、版权音乐 | 需运营商/服务商/版权授权 | 做发送记录与模板管理；实际发送走第三方适配器 |
| 4 | 第三方系统**界面素材/文案/截图** | 知识产权风险 | 只参考信息架构与字段；自建设计语言与文案 |
| 5 | **历史数据迁移** | 没有源库结构/导出文件 | 先做导入模板与校验；拿到数据后做映射 |
| 6 | 27 张报表**列头/公式** | 账号封禁 + 未点查询；公式未公开 | 解封后补采；公式由财务确认后实现 |

### 4.2 契约要求

> **艺人域写入方向**：按 10 号文档 §8 裁定（2026-11-01），艺人档案/报备/上下钟/台费/台票/`artist_setting` 均由 **App 写、CMS 投影**；PC 页面若允许编辑，必须走 `command.artist_setting.update`，由 App 应用后回传 `master.artist_setting.*`（PC 是否可写待确认）。
> 在确认前，CMS 不实现艺人 CRUD，只做只读查询/报表/导出；艺人设置页按 10 号规范做展示与受控配置。

- **查询契约**：`storeId` + `businessDateFrom/To` + 业务维度（区域/类型/支付/来源/人员）+ `page/pageSize`
- **响应契约**：`total`、`rows`、`summary`（金额/数量）、`source`（db/mock）、`businessDate`
- **导出契约**：与查询同参 + `operator` + `requestId`，写 `export_audit`
- **权限**：接口级校验（不能只隐藏菜单）
- **门店隔离**：所有查询强制带 `storeId`，越权 403
- **口径**：`businessDate` 由服务端统一计算（08:00 切日）

### 4.3 报表口径字典（v0 必填项）

| 口径项 | 待确认内容 |
| --- | --- |
| 营业日 | 08:00–08:00 是否全店统一；跨零点归属 |
| 退款/退货 | 是否从实收、数量中扣除（手册已注明“已扣除”） |
| 赠送/免单 | 是否计入营业额；是否显示金额 |
| 挂账 | 是否计入实收；担保人字段 |
| 经理打折 | 是否剔除不打折商品 |
| 交接班 | 营业额/交接款/各支付方式拆分 |
| 版权费/服务费 | 计算基数与费率 |
| 业绩系数 | 订台/导购/艺人业绩加权规则 |
